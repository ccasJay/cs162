# doc-check

请根据以下标准审查当前设计文档。目标是指出不符合要求、结构不完整、边缘情况覆盖不足、或表述不够令人信服的问题；不要替我重写整篇文档，除非我明确要求。

如果我没有指定文档路径，请优先检查当前仓库根目录下名称包含 `design`、`doc`、`设计` 的 Markdown 文档。

## 审查输出格式

请用中文输出，按严重程度组织：

1. **必须修改**：违反硬性要求、结构缺失或会让相关章节失效的问题。
2. **建议修改**：影响说服力、完整性或边缘情况覆盖的问题。
3. **可选优化**：排版、表达、可读性或篇幅控制建议。
4. **检查清单**：用简短 checklist 总结是否满足每项要求。

每个问题都要尽量包含：

- 文档位置或章节名。
- 具体问题。
- 为什么不满足要求。
- 如何修改，给出方向即可，不要大段代写。

## 基本格式与限制

- 文档总长度绝对不能超过 15 页；如果无法直接判断页数，请提醒我导出或在 Dropbox Paper 中确认。
- 不应插入大段代码块。
- 文档应保持整洁、排版良好。
- 内容尽可能的言简意赅
- 除 Concept Check 外，必须为每个 Task 创建独立章节。
- 每个 Task 章节必须包含以下四个子部分：
  - Data Structures and Functions
  - Algorithms
  - Synchronization
  - Rationale

## 每个 Task 的审查标准

### 1. Data Structures and Functions

检查是否列出所有计划新增或修改的：

- `struct` 定义。
- 全局变量或静态变量。
- `typedef`。
- 枚举。
- 关键函数签名或被修改函数。

要求：

- 必须使用 C 语言描述，不能用伪代码代替。
- 每个新增或修改项都应有简短说明，例如单行注释，解释用途。
- 如果正文算法里提到了新字段、新全局变量或新函数，但本节没有列出，要指出遗漏。

### 2. Algorithms

检查算法部分是否：

- 主要使用文字解释实现方案；如果只有代码或伪代码、缺少文字解释，要标记为必须修改。
- 抽象层级合适：比项目 spec 更具体，但不是逐行代码解释。
- 必要时使用小段伪代码或 C 片段辅助，而不是大段代码。
- 说明设计如何满足所有项目要求。
- 覆盖关键边缘情况。
- 在需要时指出相关 Pintos 源码位置或函数。

重点寻找：

- 只是复述 spec、没有说明实际实现路径的段落。
- 没有说明错误路径、边界输入、资源耗尽、线程退出、失败回滚等情况。
- 算法描述与 Data Structures and Functions 中列出的数据结构不一致。

### 3. Synchronization

检查同步部分是否：

- 列出所有跨线程或跨进程共享资源。
- 说明每个共享资源的访问环境，包括是否可能在中断上下文中访问。
- 描述如何避免竞态条件和死锁。
- 避免使用过于粗粒度且没有理由的锁。
- 对不需要同步的部分明确给出理由；未给理由时应标记为必须修改。
- 评估同步策略的时间和空间开销。
- 评估是否严重限制内核、用户进程或用户线程的并发性。
- 说明资源争用频率，以及允许同时进入独立临界区的线程数量上限或并发程度。

必须特别检查这些点：

- 中断处理程序不能获取锁；如果中断中访问同步变量，应考虑禁用中断并说明理由。
- 锁不能防止线程被抢占；不要把锁描述成禁止中断或禁止调度。
- 内存释放也是同步问题；如果使用指向 `struct thread` 的指针，必须证明使用期间对应线程不会退出并被释放。
- 新增函数如果访问全局或静态变量，必须说明两个线程同时调用时不会有同步问题。

### 4. Rationale

检查设计理由是否：

- 解释为什么当前方案优于考虑过的备选方案。
- 或者坦诚指出当前设计的缺点与取舍。
- 从以下维度评估：
  - 概念上是否容易理解。
  - 编码工作量。
  - 时间复杂度。
  - 空间复杂度。
  - 未来扩展附加功能的难易程度。

重点寻找：

- 只有“这样更简单”但没有解释为什么的段落。
- 没有任何备选方案对比。
- 没有复杂度分析。
- 没有说明当前方案的缺点或适用边界。
